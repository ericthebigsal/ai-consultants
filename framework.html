Our delivery methodology

How work moves end to end

Ten core skills, not a flat list: eight sequential stages that loop — each with a contract for what it consumes and what it hands off — plus two cross-cutting skills that attach into several stages rather than owning a step of their own. This is both how we intend to run our own engagements and the methodology behind Pillar 05 — AI in the SDLC.

01

The loop

It's a cycle, not a pipeline with an end. Maintenance doesn't close the project — it generates the next cycle's Business Requirements.

02

The eight stages

Same four fields for every stage: what it takes in, what it hands off, what makes that handoff valid, and where it goes next. That's the contract.

Stage 1

Business Requirements

Input

Discovery findings (the conversation on Problem space) — or, on a repeat cycle, the prior cycle's Maintenance signals.

Output

A written requirements document: goals, target users, success metrics, and must/should/could priorities.

Definition of done

Every requirement is measurable in principle and traces to a business outcome; a named business stakeholder has signed off.

Feeds into

UX Design and Functional Specification.

In practice

Internally, this is the write-up we produce after a discovery conversation. At a client, it's the artifact their product owner signs before any design or engineering starts — the thing that keeps "AI would be cool here" from becoming a requirement on its own.

Stage 2

UX Design

Input

Business Requirements — goals, users, success metrics.

Output

Flows, wireframes or prototypes, and every user journey described including its error and empty states.

Definition of done

Every requirement maps to a flow; edge cases are designed, not left for engineering to improvise; validated with at least a lightweight usability check.

Feeds into

Functional Specification.

In practice

For an AI-assisted feature specifically, this is where we decide what the user sees while a model is "thinking," what a wrong answer looks like, and how a user corrects it — the step most playground-built AI features skip entirely.

Stage 3

Functional Specification

Input

Business Requirements + UX Design.

Output

An implementation-ready specification: system behaviors, business rules, and explicit out-of-scope.

Definition of done

An engineer who wasn't in the room could implement it without guessing; both business and engineering have signed off.

Feeds into

Architecture and Test Plan.

In practice

For an AI-assisted feature, this is where expected failure behavior gets defined (see Error Handling, §03) — not left as an implicit assumption that the model "just works."

Stage 4

Architecture

Input

Functional Specification.

Output

A system/component diagram — boundaries, data flow, integration points, and where observability hooks in.

Definition of done

Every functional requirement maps to a component; every external dependency and failure boundary is drawn, not assumed.

Feeds into

Test Plan and Test-First Development.

In practice

For AI-touched systems, this is where we draw the model/provider boundary explicitly — which matters directly for Pillar 04: you can't migrate a boundary you never drew.

Stage 5

Test Plan

Input

Functional Specification + Architecture.

Output

Acceptance criteria and test cases — unit, integration, end-to-end — written before code.

Definition of done

Every functional requirement has at least one test case; the boundary between test types is explicit.

Feeds into

Test-First Development.

In practice

For AI-assisted behavior, this is where we write eval cases, not just unit tests — a test plan for model-driven output looks different from one for deterministic code, and pretending otherwise is the "playground, not production" failure mode from Pillar 02.

Stage 6

Test-First Development

Input

Test Plan + Architecture.

Output

Working code — tests written first (or red/green/refactor alongside), passing, reviewed against the Functional Specification.

Definition of done

Every test-plan case passes; code review is complete; no untested path reaches Deployment.

Feeds into

Deployment.

In practice

This is the production bar from Pillar 02, applied literally: an AI-assisted feature gets the same review rigor as anything else, no exception for "the model wrote most of it."

Stage 7

Deployment

Input

Reviewed, tested code + a release plan — environments, rollback path.

Output

Running software in the target environment, a release note, and a verified rollback.

Definition of done

Rollback is tested, not assumed; monitoring and alerting are live before traffic fully cuts over.

Feeds into

Maintenance.

In practice

For a platform migration (Pillar 04), this stage is the migration — cutting a team over to the golden provider with a real rollback path, not a one-way door.

Stage 8

Maintenance

Input

The running system, its logs and error signals, and user or business feedback.

Output

Incident reports, usage and cost data, and a prioritized list of fixes or new needs.

Definition of done

Every production incident has a root cause and a decision; recurring signals get promoted back into Business Requirements.

Feeds into

Business Requirements — closing the loop.

In practice

This is also where Pillar 03 (cost efficiency) lives day to day: spend and usage data reviewed here becomes next cycle's requirements, not a separate annual audit.

03

Cross-cutting: Logging & Error Handling

These don't get their own position in the loop. They attach as a requirement into several stages' contracts — which is a different (and stricter) kind of contract: not input/output, but a guarantee every attached stage has to meet.

Cross-cutting

Logging

Attaches to

Architecture (where events are emitted), Test-First Development (what gets logged and how), Deployment (routing and alerting), Maintenance (what actually gets read).

Contract it enforces

Every component named in the architecture emits structured, correlatable events at defined points, and logging is live before a release ships — not bolted on after the first incident.

In practice

For an AI-assisted feature, this includes the specific inputs, outputs, and model/version used per request. Without it, "why did it say that" is unanswerable after the fact.

Cross-cutting

Error Handling

Attaches to

Functional Specification (expected failure behavior), Architecture (failure boundaries), Test-First Development (failure paths are tested, not assumed), Deployment (a rollback is a designed error-handling case, not an emergency improvisation).

Contract it enforces

Every failure mode identified in the architecture has a defined, tested behavior; no unhandled path reaches a user.

In practice

For AI-assisted features specifically, a wrong, slow, or unavailable model response is a failure mode like any other — designed for at UX Design, not discovered in production.

04

Still open

Open: whether every client engagement runs the full eight-stage loop, or whether a narrow engagement (e.g. a Pillar 04 migration touching only Stages 6–8) can legitimately skip the earlier stages rather than retrofit them. Also open: whether this framework is something we hand to a client as-is, or a lens we apply without necessarily naming it to them. See the master list on Engagement → open questions.
