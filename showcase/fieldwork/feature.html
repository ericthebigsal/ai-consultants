Part 02

Response quotas per audience segment

One feature, walked from the paragraph a PM wrote to the PR that shipped it. Every artifact Claude Code produced is listed, and every point a person had to sign off.

medium feature 8.5 working days 6 gates, all passed

The requirement, as written

“Survey owners need to cap how many completed responses come from each audience segment, so the final sample matches a target distribution. Example: stop collecting from ‘men 45+’ once we hit 200 completes, but keep the survey open for everyone else. When a quota is full, those respondents should be screened out politely before they start. Owners set quotas when building the survey and can adjust them while it’s live.”

— PM, in the feature ticket

The walk

  1. Claude CodeRequirementsday 1–2

    Expanded the ticket into the requirements doc: the quota model (segment + target + current count), the live-adjust rules, the screen-out copy, the reporting need, and four open questions — including “what counts as a ‘complete’ for the quota: submitted, or passed validation?”

    artifact: docs/features/segment-quotas/requirements.md

    Requirements sign-off — PM answered the open questions (a complete is a validated submission) and approved.
  2. Claude CodeFunctional specday 2–4

    Wrote the spec against the codebase: quotas attach to a survey as a new quota_group; the logic engine checks quota state at screen-in; a live counter updates on each validated complete; owners edit quotas from the existing survey-settings panel. Flagged a race condition — two respondents completing at once near the cap — and proposed handling it.

    artifact: docs/features/segment-quotas/spec.md

    Spec review — eng lead accepted the approach, chose the stricter race handling (a short lock at the cap), PM confirmed the screen-out flow.
  3. Claude CodeArchitectureday 4–5

    Proposed the schema: a quota_groups table and a quota_counts table keyed by group and segment, with the count incremented in the same transaction as the response write. Sketched the migration and the backfill (none needed — new tables). Noted the response-pipeline touch and routed it for extra review.

    artifact: migration 0412_quota_groups.sql (draft), architecture note in the spec

    Architecture review — architect approved the schema; the pipeline change got a second reviewer per the guardrails.
  4. Claude CodeTest planday 5

    28 test cases from the spec: unit tests for quota-state math, integration tests for screen-in with a full quota, a property test that total completes per segment never exceeds its target under concurrent load, and a manual pass for the screen-out copy. Each case mapped to a requirement line.

    artifact: packages/logic/src/quotas/__tests__/ (plan), test-plan doc

    Test-plan review — QA added two cases (quota edited to below the current count; quota deleted mid-survey) and approved. Plan merged.
  5. Claude CodeBuildday 5–8

    Five PRs, test-first each time: the schema + migration; the quota-state module; the logic-engine screen-in check; the settings-panel UI; the reporting column. Ran typecheck, tests, and the survey-logic property suite on every push. Two design questions surfaced (should an edited quota retroactively screen out over-target completes? — no) and were answered in review, not deferred.

    artifact: PRs #4021–#4025

    Code review — each PR reviewed and approved by an engineer. Same bar as any change.
  6. Claude CodeDeploymentday 8–8.5

    Prepared the release: notes, the migration run order (tables first, then the feature flag), a rollback checklist (flag off, tables can stay), and a load-test plan for the pipeline change.

    artifact: docs/releases/2026-w37-segment-quotas.md

    Release sign-off — on-call engineer ran the load test, then the deploy, and enabled the flag for 5% of surveys. Claude Code did not touch production.

What to notice

  • Claude Code produced every first-draft artifact. A person reviewed and owned every one.
  • The two hard calls — the race condition, the retroactive-screen-out question — were surfaced early and decided by the people who should decide them.
  • The pipeline touch got the extra review the guardrails require, automatically, because the setup routes it.
  • Nothing about the process is new. It's the same six stages and six gates, done in 8.5 days instead of 20.
