Per stage — what changed

  1. 1

    Requirements — 3d → 2d

    Claude Code draftsThe requirements doc from the discovery notes and the PM's bullet points, in Fieldwork's template, with the open questions called out.
    The PM decidesScope, priority, the success metric, and answers to the open questions. Signs the doc.
    Requirements sign-off — a named PM approves before design starts.
  2. 2

    Functional spec — 4d → 1.5d

    Claude Code draftsThe spec from the requirements plus the codebase — existing patterns, the affected modules, explicit out-of-scope, edge cases in the logic engine.
    The eng lead decidesWhether the approach fits, resolves any ambiguity the draft flagged, cuts or adds scope.
    Spec review — eng lead and PM both approve. This is the biggest single time saving.
  3. 3

    Architecture — 2d → 1d

    Claude Code draftsThe component and data-model changes against the real schema (via the read-only staging-schema MCP), with the migration sketched and failure boundaries drawn.
    The architect decidesThe final shape, the migration strategy, and anything touching the response pipeline.
    Architecture review — required for any schema or pipeline change.
  4. 4

    Test plan — 2d → 0.5d

    Claude Code draftsThe test cases from the spec — unit, integration, and property tests for the quota logic — and maps each back to a requirement.
    QA decidesCoverage — what's missing, which edge cases are real, what needs a manual pass.
    Test-plan review — QA approves; the plan is merged before any implementation PR.
  5. 5

    Build (test-first) — 8d → 3d

    Claude Code draftsThe implementation in a red-green-refactor loop against the merged test plan, one reviewable PR per slice, running the repo's checks each time.
    Engineers decideEvery PR is reviewed and approved by a person. Design calls the model surfaces get answered, not deferred.
    Code review — every PR, same bar as any other change. No PR merges without a human approval.
  6. 6

    Deployment — 1d → 0.5d

    Claude Code draftsThe release notes, the migration run order, and the rollback checklist.
    The on-call engineer decidesWhen to ship, runs the deploy, watches the dashboards.
    Release sign-off — a person runs the deploy. Claude Code never deploys to production.

How the number is real

  • Phase 0 baselines the current cycle across the last ten shipped features — time per stage, PR count, review turnaround, and the post-release defect rate.
  • After each stage is integrated, the same metrics are tracked for every feature that runs through it.
  • The acceleration only counts if the defect rate holds. If it moves, the gate that let it through gets tightened, not removed.
The saving is in drafting, not deciding. Every gate on this page existed before Claude Code and still does. What compresses is the time spent producing the artifact that the gate reviews.
