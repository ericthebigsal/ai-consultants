Two vendors gone, three teams moved, nothing they built stopped working.

The vendor analysis ended on a recommendation: consolidate on Vendor A, on the higher-tier plan that fixes the rate limits that caused the sprawl. 01 · The inventory

What each team actually did with B and C

Not the sanctioned use — the real one. You can't rebuild a workflow you haven't seen, and the thing that breaks a migration is always the use nobody wrote down.

Create Inventoried every call to B and C from the codebases, the notebook repo, and a month of API logs — the prompt, the model, the response fields read, and any vendor-specific feature — then interviewed each owning team against that draft. confirming the inventory was complete, and that no workflow was missing.

03 · Cutover

The order, and what pulls it back

Accelerate Drafted the cutover sequence from the dependency map — thinnest and lowest-risk first, the agent last — with a dual-run window and a rollback trigger written for each step. the schedule against each team's week, and the call to advance or roll back at every step.

3 · In-app summarizationProduct Eng3 daysQuality sample below 8.0
4 · Report-builder agent (2 features)Product Eng1 week behind a flag: 10% → 50% → 100%Any tool-call contract test failing in production
Timeline. Vendor C fully dark in week 1 — well ahead of its August renewal. Vendor B fully dark in week 3; the non-renewal notice went out inside the 60-day window before the January date. No workflow ran on both vendors for longer than its dual-run window.

04 · Decommission

Gone, not just unplugged

Maintain Tracked the shutdown checklist to closure — keys, SSO apps, contracts, logs, budget lines — and watches the expense feed and SSO list so a revived account would show up within the week. the non-renewal notices, and the sign-off that each account is actually closed.
  • done Vendor C API keys revoked, SSO app removed
  • done Vendor C contract left to lapse at the August renewal; finance notified
  • n/a Vendor C — no DPA to unwind, no data held to export
  • done Vendor B API keys revoked, SSO app removed
  • done Vendor B non-renewal notice sent inside the 60-day window before January
  • done Vendor B prompt and response logs exported for the 90-day retention window, then deletion requested
  • done Budget lines for B and C closed; the Vendor A plan upgrade booked against the saving
Still open, on purpose. Vendor E (meeting transcription) is not part of this migration — it's on the governance track, paused until a DPA is signed or it's replaced. Listed here so it isn't mistaken for finished work.

The next platform decision stays with Northwind

What we hand over so the next vendor call doesn't need us:

  • The scorecard method. The five criteria and their weights, and the held-out prompt sample, so any new vendor is scored on Northwind's real workloads, not a benchmark.
  • “Why not an existing vendor?” The one-line question every new AI-tool request answers before it's approved — the same gate the register and the controls use.
  • Dual-run before cutover. No vendor swap goes straight to 100%; every one gets a shadow window and a written rollback trigger.
  • The renewal calendar. Every contract's renewal and notice date, with a 60-day reminder and current usage attached.
The honest limit. This went cleanly because A, B, and C were interchangeable general LLM APIs — the differences were price, limits, and paperwork. Migrating between vendors with genuinely different capabilities, or off a platform your product is built into, is a longer job, and we'd scope it as its own engagement rather than pretend it's a config swap.
