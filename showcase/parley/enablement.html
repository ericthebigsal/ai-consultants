Deliverable 04

Keeping the bar enforced after we leave

A production bar is a wiki page within a month unless it's wired into the tools engineers already use and owned by someone inside the company. This is the machinery that keeps it real: a CI gate, a review checklist, a pattern library from Parley's own code, and one standing review.

1 CI gate 4 PR checkboxes 4 reusable patterns quarterly re-check

01 · The CI eval gate

The one rule that can't be a checkbox

Grounding, logging, and ownership are things a reviewer can verify by reading a diff. “Is it actually good?” isn't — so it runs in CI.

  • shared One eval harness in the monorepo. A feature registers its question set, its graders, and its written bar; the harness runs them the same way for every feature.
  • blocking On a PR that touches an AI feature, its eval runs and must clear the feature's bar. A regression fails the build with the specific cases that dropped.
  • visible The eval result posts to the PR — before and after numbers — so a reviewer sees the quality impact next to the code.
  • seeded Ticket triage, conversation summary, and the answer bot ship with their eval sets from this engagement. Suggested replies gets one during its harden.

02 · The review checklist

Four lines in the PR template

Drafted Written as the shortest checklist that covers the four non-eval rules, in the language of Parley's existing PR template — which already has blocks for schema changes and feature flags. which lines block a merge and which are advisory, and who the default reviewer is for an AI change.

Reviewers also get a one-paragraph “what to look for in an AI change” note in the contributing guide — the same treatment schema migrations already have.

04 · The half-day

Trained on their codebase, not a course

One half-day session with the three teams that own AI features. The material is Parley's own: the six features as worked case studies, the bar with its real pass/fail examples, and the pattern library live in the repo. Engineers leave having run the eval harness against a feature and added a guardrail to it, not having watched slides about prompt engineering.

The honest scope. The session doesn't make anyone an ML engineer. It makes the people already shipping AI features able to tell a demo from a dependency, and gives them the checklist and the tools to close the gap.

05 · The quarterly re-check

Because the inputs move even when the code doesn't

The most common way an AI feature degrades is that a data source changed and no one re-ran anything. One standing review catches it.

  • sample Each live AI feature is re-scored against a fresh sample of real production traffic, using its own eval graders.
  • diff The result is diffed against last quarter. A drop opens a ticket to the named owner with the regressed cases attached.
  • register Any new AI feature since last quarter is added to the inventory and checked against the bar.
  • owner One named person at Parley runs the review. It's on the platform team's calendar, half a day a quarter.

What we hand over

The whole kit

Delivered. The inventory wired to the codebase scan; the production bar in the PR template and contributing guide; the CI eval harness with three features seeded; the triage with every verdict and its reasoning; the answer-bot hardening shipped and its runbook; the pattern library; and the quarterly re-check on the calendar with a named owner. Then we leave.
How you know it held. Six months on, a new AI feature goes through the same review as any other change — no special exception, no special fear — and the quarterly re-check has caught at least one drift before a customer did.
