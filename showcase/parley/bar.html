The bar

Five rules for shipping AI-assisted work

Drafted Written against the real failure patterns in the inventory — not a generic checklist. Each rule exists because a shipped feature already broke it. the wording, which rules are blocking vs. advisory, and the blast-radius threshold for “needs all five.”
  • 1 · Grounded or labelled

    Customer-facing factual output is either grounded in a cited source, or clearly presented as a draft or suggestion a named person owns. No unsourced assertions reaching a customer as fact.

    passSuggested replies — shown as an editable draft; the agent owns the send.
    failAnswer bot — states billing and policy specifics with no citation and no “this is automated” framing.
  • 2 · Evaluated before merge

    An AI feature ships with an eval suite that runs in CI, a written quality bar, and a baseline to beat. A PR that moves the metric shows the number moving.

    failAnswer bot — zero eval, live to 100% of eligible tickets for nine months.
    failMacro suggestions — never measured; the “wrong ~15% of the time” number came out of this audit, not from monitoring.

    No feature clears this rule today. It is the single biggest gap and the reason two features are being retired rather than kept.

  • 3 · Human gate on action

    Model output that sends a message, changes state a customer sees, or closes a conversation is reviewed by a person — unless its eval clears a higher bar and the feature is monitored in production.

    passSuggested replies — the agent reads and sends; the model never sends.
    failTicket triage — silently sets priority and routing; a mis-route on a P1 outage ticket has cost real response time twice.
  • 4 · Logged and attributable

    Every model call logs the prompt version, the model and version, the input class, and the outcome. Retained 90 days. A bad output can be traced to the exact inputs and prompt that produced it.

    passConversation summary — logs prompt version and input class; a wrong summary is reproducible.
    failAnswer bot — no record of which help-center revision it answered from, so a stale answer can't be traced.
  • 5 · Owned

    Every AI feature has a named owner and a review cadence. The owner is who notices the day a data source changes and the outputs quietly degrade.

    passConversation summary — named owner, reviewed two months ago.
    failSentiment flagging — no owner; nobody noticed its false-negative rate for a year.

How it folds in

Four checkboxes and a gate, not a new committee

The bar is worthless as a wiki page nobody opens. It lives in the two places engineers already are: the PR template and CI.

  • PR A short “AI-assisted change” block in the PR template: grounded/labelled, human gate, logging, owner — check or justify.
  • CI The eval gate: if the feature has an eval, it runs on every PR and blocks merge below the written bar. Rule 2 can't be a checkbox because it's the one people fudge.
  • review Reviewers get a one-paragraph “what to look for in an AI change” note — the same way they already have one for a schema migration.
  • quarterly One standing review: each AI feature re-checked against a fresh sample of real traffic. Covered on Enablement.
Blast-radius scaling. A model whose output a person always edits before it goes anywhere needs rule 1 and an owner. A model that auto-sends to a customer or closes a ticket needs all five, no exceptions. The threshold is written down so it isn't argued per PR.
